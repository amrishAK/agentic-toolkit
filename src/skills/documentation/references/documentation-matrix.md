# Documentation selection matrix

## Document and topic reference matrix

| Document or topic | Default location | Purpose | Owner and update trigger | Rules and related workflows |
|---|---|---|---|---|
| README | `README.md` | Entry point: purpose, status, first supported workflow, development entry points, and deeper docs | `project-standardizer` for confirmed setup; documentation writer thereafter. Update for entry-point, navigation, or supported-usage changes. | [Documentation layout](documentation/docs-layout.md#readme-and-documentation-index), [project tracking](documentation/project-tracking.md) |
| Repository profile | Existing equivalent, otherwise proposed root `project-profile.yaml` | Structured repository purpose/layout, deliverables, languages, build systems, CI/CD, and intended platforms; not executable configuration or validation evidence | `project-standardizer`. Update affected fields with authorized setup or technical-profile changes; audit without edits. | [Profile format and example](../../project-standards/references/project-rules-workflow-repository-profile.md), [profile-first setup workflow](../../project-standards/project-rules-workflow.md) |
| Documentation index | `docs/README.md` | Task/audience navigation to canonical docs when documentation spans audiences | `project-standardizer` for confirmed setup; documentation writer thereafter. Update when navigation changes. | [Documentation layout](documentation/docs-layout.md#readme-and-documentation-index) |
| Agent guide and scoped instructions | `AGENTS.md`, established scoped-instruction locations | Essential navigation, agent operations, and confirmed project rules | `project-standardizer`. Update when rules, authorities, or navigation change. | [Agent-guide outline](../../project-standards/references/project-rules-workflow-agents-md-outline.md) |
| Product overview | `docs/project-overview.md` | Vision/pitch: problem, value, audience, usage, boundaries, and non-goals | `product-planner`. Update when direction or boundaries change. | [Product overview](documentation/product-overview.md), [product planning](../../design-and-planning/product-planning-workflow.md) |
| Roadmap | `docs/status/roadmap.md` | High-level direction and priorities, not release progress | `product-planner`. Update when priorities or milestones change. | [Roadmap documents](documentation/roadmap-docs.md), [roadmap planning](../../design-and-planning/roadmap-planning-workflow.md), [product planning](../../design-and-planning/product-planning-workflow.md) |
| Known issues | `docs/status/known-issues.md` | Confirmed bugs and limitations only | Follow the project's established owner. Update when a known issue is confirmed or its status changes. | [Known-issues documents](documentation/known-issues-docs.md) |
| Decision log | `docs/status/decisions.md` | Concise index of important user, product, and technical decisions, with links to canonical records | Decision owners. Update when an important decision is made, confirmed, rejected, or superseded. | [Decision log](documentation/decision-log.md), [architecture documents](documentation/architecture-docs.md) |
| Technical-debt register | `docs/status/technical-debt.md` | Confirmed engineering liabilities, impact, ownership, state, and remediation links | Accountable engineering owner. Update when debt is confirmed or its impact, priority, state, or remediation changes. | [Technical-debt registers](documentation/technical-debt-docs.md), [known issues](documentation/known-issues-docs.md) |
| Feature document | `docs/proposals/` | Active detailed contract: behavior, edge cases, observable acceptance criteria, design, and open decisions | `feature-designer`. Update on contract/design changes; consolidate completed release scope in versioned notes and remove superseded files when notes are ready. | [Feature documents](documentation/feature-docs.md), [release consolidation](documentation/release-notes.md#consolidate-feature-documents), shared [feature design and review workflow](../../design-and-planning/feature-design-workflow.md); [architecture workflow](../../design-and-planning/architecture-workflow.md) when relevant |
| Feature tracker (when adopted) | `docs/status/features.md` | Source of truth for implementation state and supporting evidence, distinct from feature-document decision status and release-gate status | `feature-designer` for intended scope; implementer for progress. Update when work starts, finishes, is deferred, or dropped. | Default convention; confirmed project rules may opt out. See [project tracking](documentation/project-tracking.md) and [feature design](../../design-and-planning/feature-design-workflow.md). |
| Architecture | `docs/architecture/` | Implemented design and durable decisions, not proposals | `feature-designer` for proposed decisions; `code-engineer` for implemented changes. Update when a significant boundary, interface, lifecycle, or decision changes. | [Architecture documents](documentation/architecture-docs.md), [architecture workflow](../../design-and-planning/architecture-workflow.md) |
| API, protocol, and data contracts | Project-established API/reference location; otherwise active proposed behavior belongs in its feature document under `docs/proposals/`, and a durable implemented reference defaults to `docs/reference/` | Contract for readers integrating with or exchanging data with a public API, protocol, or persisted/interchanged schema. Cover applicable versions, inputs and outputs, field/encoding semantics, errors, compatibility, and representative examples; link to the implementation and verification evidence without presenting intended behavior as observed. Keep one canonical contract rather than copying it into source comments or guides. | `feature-designer` owns intended behavior; implementers update the documented observed contract when implementation changes. Update when the public contract or compatibility behavior changes. | [Feature documents](documentation/feature-docs.md) for proposals; [architecture workflow](../../design-and-planning/architecture-workflow.md) for significant boundaries; applicable [unit](../../testing/unit-test-workflow.md) or [integration](../../testing/integration-test-workflow.md) workflow and [language-specific skill matrix](../../programming-languages/references/programming-language-matrix.md) for verification and source-level references |
| Release plan | `docs/releases/<milestone>.md` | Milestone scope, exclusions, acceptance gates, and candidate evidence | `product-planner`. Update when planning a milestone or changing its scope. | [Release documents](documentation/release-docs.md), [release planning](../../design-and-planning/release-planning-workflow.md), [product planning](../../design-and-planning/product-planning-workflow.md), [release workflow](../../build-and-delivery/release-workflow.md) |
| Release notes | Project-established release page or versioned file, default `docs/releases/<version>-notes.md` (for example `v1.2.0-notes.md`) | User-facing, lasting summary of consolidated completed features, compatibility, upgrade actions, and known limitations | `technical-documentation-writer` from verified release contents, preserving feature contracts with `feature-designer`. Update for release preparation, feature consolidation, or published-note corrections; publication needs separate authorization. | [Release notes](documentation/release-notes.md), [technical documentation workflow](../technical-documentation-workflow.md), [release workflow](../../build-and-delivery/release-workflow.md) |
| User and developer guides | `docs/guides/` | How to complete a supported user or development task | `technical-documentation-writer`. Update when supported workflows or development entry points change. | [Guide requirements](documentation/technical-guides.md#user-and-developer-guides), [technical documentation workflow](../technical-documentation-workflow.md) |
| Setup and onboarding | `docs/guides/` | How to prepare an environment and verify the first successful workflow | `technical-documentation-writer`. Update when prerequisites, setup, or supported platforms change. | [Setup requirements](documentation/technical-guides.md#setup-and-onboarding), [technical documentation workflow](../technical-documentation-workflow.md) |
| Package and module guides | `docs/guides/` | What a module exposes, depends on, and requires for safe use | `technical-documentation-writer`. Update when public surfaces, dependencies, lifecycle, or configuration change. | [Module guide requirements](documentation/technical-guides.md#package-and-module-guides), [technical documentation workflow](../technical-documentation-workflow.md) |
| Integration guides | `docs/guides/` | How to interact with a supported external or public boundary | `technical-documentation-writer`. Update when supported versions, configuration, or boundary contracts change. | [Integration requirements](documentation/technical-guides.md#integration-guides), [technical documentation workflow](../technical-documentation-workflow.md) |
| Data and request flow | `docs/guides/` | How information moves through a system, including state and side effects | `technical-documentation-writer`. Update when stages, ordering, state, or failure boundaries change. | [Data-flow requirements](documentation/technical-guides.md#data-and-request-flow), [technical documentation workflow](../technical-documentation-workflow.md) |
| Runbooks | `docs/guides/` | How an authorized operator diagnoses and recovers from a specific condition | `technical-documentation-writer`. Update when supported diagnosis, recovery, or rollback changes. | [Runbook requirements](documentation/technical-guides.md#runbooks), [technical documentation workflow](../technical-documentation-workflow.md) |
| Troubleshooting | `docs/guides/` | How checks distinguish likely causes of an observed symptom | `technical-documentation-writer`. Update when symptoms, diagnostic evidence, or corrective actions change. | [Troubleshooting requirements](documentation/technical-guides.md#troubleshooting), [technical documentation workflow](../technical-documentation-workflow.md) |
| Migration notes | `docs/guides/` | How affected users move between versions safely | `technical-documentation-writer`. Update when supported upgrades, compatibility, or rollback limits change. | [Migration requirements](documentation/technical-guides.md#migration-notes), [technical documentation workflow](../technical-documentation-workflow.md), [release workflow](../../build-and-delivery/release-workflow.md) |
| Build, CI, and container command docs | Project-established documentation location | Prerequisites, commands, and artifacts for build, CI, or container workflows | `build-automation-agent` for coupled command changes; documentation writer for standalone guides. Update when commands, prerequisites, or artifacts change. | Relevant [build](../../build-and-delivery/build-system-workflow.md), [CI](../../build-and-delivery/ci-workflow.md), and [container](../../build-and-delivery/container-build-workflow.md) workflows |
| Testing and fixture guides | `docs/guides/` | Existing test tiers, commands, infrastructure, and fixture lifecycle | Corresponding test specialist. Update when test boundaries, runners, fixtures, or lifecycles change. | [Testing conventions](../../project-standards/references/project-conventions-testing.md), [guide requirements](documentation/technical-guides.md#user-and-developer-guides), and relevant [unit](../../testing/unit-test-workflow.md), [integration](../../testing/integration-test-workflow.md), or [E2E](../../testing/e2e-test-workflow.md) workflows |
| Benchmark methodology, reports, and evidence | Project-established benchmark/results location; for a requested durable report with no existing convention, `docs/reports/YYYY-MM-DD-benchmark-topic.md` | Explain the measurement question, workload and method, candidate/environment, comparable results and uncertainty, and limits. Keep raw results in the established artifact location; do not turn an isolated measurement into an unsupported performance claim. | `benchmark-engineer` owns methodology and results. Update when workloads, methods, candidates, or measurements change; a writer records only supplied, verified results. | [Benchmark workflow](../../performance/benchmark-workflow.md), [technical documentation workflow](../technical-documentation-workflow.md), and [language-specific skill matrix](../../programming-languages/references/programming-language-matrix.md) |
| Incident and investigation reports | `docs/reports/YYYY-MM-DD-topic.md`, unless the project has an established or restricted location | Use for a requested or project-required durable investigation record, not automatically for every incident. Capture the symptom and impact, relevant timeline and investigation evidence, confirmed cause (or labeled hypothesis), corrective action/recovery, verification, and follow-ups. Distinguish facts from inference, link evidence where safe, and exclude secrets or sensitive incident details. Keep operator procedures in runbooks rather than duplicating them here. | Follow the project's established incident/operations owner; no cross-project owner is assumed. Update when findings, verification, or follow-ups change; record only verified or clearly qualified findings. | [Documentation layout](documentation/docs-layout.md#what-goes-where), [debugging workflow](../../implementation/debugging-workflow.md), and [technical documentation workflow](../technical-documentation-workflow.md) |
| Contribution and security policies | `CONTRIBUTING.md`, `SECURITY.md` | Adopted contribution process and private vulnerability reporting | `project-standardizer` for confirmed setup; documentation writer for later prose. Update when the maintainer adopts or changes policy. | [Community documents](documentation/community-docs.md), [open-source baseline](../../project-standards/references/project-conventions-oss-baseline.md), project-rule safeguards |
| Changelog | `CHANGELOG.md` | Curated notable user-visible changes per release | `project-standardizer` for confirmed setup; documentation writer for later prose. Update according to adopted release policy. | [Community documents](documentation/community-docs.md) |
| Issue and PR templates | `.github/ISSUE_TEMPLATE/`, `.github/pull_request_template.md` | Contribution templates consistent with adopted policy | `project-standardizer` for confirmed setup; documentation writer for later prose. Update when the maintainer adopts or changes policy. | [Community documents](documentation/community-docs.md) |
| License and ignore rules | `LICENSE`, `.gitignore` | Confirmed license text and ignore rules; not prose templates | `project-standardizer` for confirmed setup; later changes follow the project's established owner. Update when adopted policy or ignore requirements change. | [Project-rule safeguards](../../project-standards/project-rules-workflow.md#license-and-ignore-file-safeguards) |
| Source API comments, rustdoc, and Doxygen | Relevant source files | Public source contracts and non-obvious safety, ownership, or behavior details | `source-documentation-writer`; implementer for coupled updates. Update when exposed contracts or safety/ownership explanations change. | [Language-specific skill matrix](../../programming-languages/references/programming-language-matrix.md) |
| Agent and skill definitions | Established source location | Agent roles, skills, and their workflows | User-authorized customization task. Update when roles, workflows, metadata, or supported clients change. | Follow [definition-authoring guidance](../../../../docs/reference/definition-authoring.md) and applicable host/project instructions. |
| Commit, pre-PR, and release-readiness reviews | Not persisted by default | Independent, read-only readiness findings | `change-reviewer`. Review when a change or candidate is submitted. | [Review workflow](../../review-and-security/review-workflow.md), [release workflow](../../build-and-delivery/release-workflow.md) when relevant |
| Security assessment and threat model | Project-established location, if documented | Authorized security findings or threat analysis | `security-reviewer`, read-only. Update when an authorized security review is requested. | [Security review](../../review-and-security/security-review-workflow.md) |
| Test, benchmark, and release-gate evidence | Project-established results/artifact location; release gates belong in the milestone document. Record evidence only where the project requires or adopts it. | Candidate-specific record of the revision/dirty state, artifact and configuration, environment/toolchain, commands or scenarios, actual results (including failures and skips), evidence links, and limitations. Release-gate state belongs to the release document, not the feature tracker; an implemented feature or absent result is not a passed gate. | The relevant specialist executes checks; the release/gate owner assesses them; an authorized writer records supplied results. Refresh evidence when the candidate or relevant checks change. | [Release document evidence and validation](documentation/release-docs.md#validation), [release workflow](../../build-and-delivery/release-workflow.md), applicable [unit](../../testing/unit-test-workflow.md), [integration](../../testing/integration-test-workflow.md), or [E2E](../../testing/e2e-test-workflow.md) workflow, and [benchmark workflow](../../performance/benchmark-workflow.md). Do not create a separate evidence catalogue by default. |
