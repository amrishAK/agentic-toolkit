# Software product development task workflow

## When to use

Use this skill for the shared software product development task cycle, including task framing, evidence, guidance selection, role boundaries, validation, and reporting.

## Scope and boundaries

Use this common task cycle with the active agent's role-specific procedures across product management, engineering, and quality. The canonical skill name remains `engineering-task-workflow` so existing role links and invocations continue to work. It does not replace specialist workflows or grant permission to act.

## Procedure

### Common task cycle

1. **Frame the task.** Identify the requested outcome, the active role, and the mode of work: discussion/design, review, implementation, documentation update, or validation. Follow any more specific mode defined by the active role.
2. **Establish context.** Read the applicable project instructions and authoritative sources. Distinguish current behavior and accepted decisions from proposals, assumptions, and unresolved questions.
3. **Select guidance.** Keep workflows required by the active role in force. For additional guidance, follow the shared [skill selection workflow](../agent-workflows/skill-selection-workflow.md) to select and acquire only what applies to the task. Report unavailable guidance without substituting another skill or claiming it was applied.
4. **Resolve material gaps.** Surface conflicting evidence and missing guidance. Ask one focused question when an unresolved decision materially affects correctness, scope, or safety; otherwise state a bounded assumption and proceed only when the role permits.
5. **Work within the role boundary.** Perform only the requested mode of work. Reviews remain findings-only; discussion does not create unsolicited artifacts; implementation and document updates remain subject to the active role's authorization. A handoff conveys context and a requested next decision or action; it does not itself approve or execute that action.
6. **Validate and report.** Check the requested outcome with the smallest relevant evidence or validation available. Report what was done, exact checks and results, limitations, and what remains unverified. Do not describe a proposal as implemented or a check as passed without evidence.

Specialist workflows define additional steps and boundaries for their domains. Where they are more restrictive or task-specific, follow them.
