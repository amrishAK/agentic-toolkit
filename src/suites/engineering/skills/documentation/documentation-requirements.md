# Documentation requirements

This skill is the document catalogue and rule selector, not a workflow. Use it before touching any document to answer:

- **What is this document?** Its meaning, audience, and what it must and must not hold.
- **Where does it live?** Its default location and canonical topic.
- **Who owns it and when does it change?** Its decision owner and update trigger.
- **Which rules apply?** The reference defining required content, structure, boundaries, and acceptance criteria.

The calling agent keeps its own workflow. A writer drafts against the selected rules, a reviewer assesses against them, an implementer updates against them, and a standardizer uses the catalogue to decide which documents a project needs. This skill does not prescribe research, prose style, editing steps, or reporting, and selecting a rule grants no permission to edit.

## Identify the document type

- Classify by purpose and audience, not by filename. A `README.md` inside `docs/` may be an index; a file called `overview.md` may be a vision pitch or a current-usage guide.
- Distinguish intent from state: product vision, detailed contract, current implementation, plan, operational procedure, and candidate evidence are different documents even when they cover the same feature.
- Project-owned instructions, established locations, and adopted formats override these defaults. Apply the catalogue where the project is silent, and surface conflicts rather than overriding them.
- If the type, audience, or owner is materially ambiguous, ask one focused question rather than guessing.

## Document catalogue

The catalogue covers documents, not the complete repository structure. Use [repository-wide placement conventions](../project-standards/references/project-conventions-architecture-and-scope.md#repository-layout) for code, tests, tools, manifests and outputs. The [setup workflow](../project-standards/project-rules-workflow.md) owns inspection, explanation/proposal, interview refinement, confirmation, creation of agreed essentials and validation; selecting a document here does not initialize a repository.

## Document routing and maintenance ownership

Each topic has one canonical owner. Ownership identifies the responsible decision and normal specialist, not an exclusive file lock: implementers update directly affected documentation and evidenced status in the same change. This is a default routing map, not automatic agent invocation; project-owned instructions remain authoritative and must work without this suite.

Assess baseline, release, and community documents by the project's stage and audience; see the [open-source baseline](../project-standards/references/project-conventions-oss-baseline.md). Operational guides apply only when relevant. A matrix entry is not a requirement to create the file.

- Product planning owns intent; feature design owns detailed contracts; implementation supplies current behavior and evidence; reviewers independently assess readiness. None of these roles independently approves business commitments, publication, or a release.
- Reviewers return findings without direct document edits or persisted reports. Explicit apply selections allow delegation-enabled reviewers to launch bounded editing subagents and re-review; reviewers never perform delivery actions.
- Release goals are not release results. A changed candidate reruns affected gates or explicitly justifies reused evidence.
- Feature handoffs include goals/non-goals, testable acceptance criteria, contracts, dependencies, risks, and unresolved decisions. A small, well-defined fix does not need a feature document or every specialist.

## Apply the rules

- Treat the selected rules as the document's acceptance criteria: purpose, required content, excluded content, structure, boundaries, and validation.
- Suggested headings are structure to adapt, not empty sections to create. Requirements are met by meaningful content, not matching headings.
- A missing required item is reported as unresolved, not filled with placeholders or invented facts, commitments, versions, contacts, dates, thresholds, or commands.
- A review finding cites a selected rule or a factual defect. Stylistic preference is not a missing requirement.
- Preserve the document's intended framing. A vision stays a vision with envisioned behavior labelled; it is not replaced by an implementation inventory.
- When auditing coverage, mark each relevant catalogue entry as present, create/update, deferred, not applicable, or unresolved, with the reason for anything missing.

## Rules for every document

- **One canonical owner per topic.** Other documents summarize and link with relative links; they do not copy mutable status, procedures, contracts, or evidence.
- **Keep kinds of truth separate.** Intended capabilities, detailed contracts, implementation state, release requirements, and executed evidence live in their own documents. Missing evidence is not a pass.
- **Respect decision owners.** Documentation changes must not silently make another owner's decisions.
- **Split by audience, owner, or update trigger,** not line count. Reuse an existing canonical home before creating a file. A split or move updates inbound and outbound links and removes the obsolete copy.
- **Only applicable documents.** Do not create placeholder files, trackers, or policies just because the catalogue lists them.
- **Readable navigation.** Readers reach a task and its authoritative document without circular or duplicate guidance. Use tutorials, how-to, reference, and explanation content purposefully ([Diataxis](https://diataxis.fr/)) without forcing a directory structure.
- **Validate the real format.** Check local links, anchors, heading hierarchy, and renderer compatibility. For external formats such as [GitHub templates](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/about-issue-and-pull-request-templates), [security policies](https://docs.github.com/en/code-security/how-tos/configure-and-manage-your-organization/establishing-a-security-policy), and [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), follow the actual specification. A license file or badge does not establish licensing rights.
